## 协作步骤

1. 仓库所有者在GitHub Settings → Collaborators邀请另外三位真实账号；私有仓库的成员须接受邀请。老师或AI评分服务需要查看源码时，要单独解决仓库访问权限。
2. 每人 `git clone` 仓库，以自己的账号认证；本地`user.name`和`user.email`使用本人信息及GitHub已关联的邮箱。不能把组长的配置复制给所有人。
3. 从最新main建立上表功能分支。每完成一个可运行阶段，先运行测试，再`git add`、`git diff --cached`检查改动，最后commit和push。
4. 建PR，说明功能、实际修改文件、验证步骤和结果、已知限制。另一位成员看diff并试用，再合并；演示前不强行大改主干。
5. 为保留每位成员的真实提交，优先使用保留提交记录的合并方式。若采用squash，先确认作者归属及原PR/分支历史仍可核验；不靠代签或改日期凑次数。

## 最紧验收安排

- 今晚：四人启动同一可运行基线，各用10分钟读自己负责的函数；A统筹最小改动，B/C完成独立模块，D回归和收集真实试用反馈。
- 课前至少2小时：停止加入新功能，合并已通过的改动，重跑测试、生成新exe与报告。未完成增量留在分支，不影响已冻结可运行版本。
- 课前1小时：在演示电脑冷启动exe，断网走一遍8分钟流程，确认备份/导出目录权限；四人各讲自己的一段代码。
- 若实际验收在11月9日：用第1–2天完成首轮增量，第3–4天合并/测试，第5天真人反馈，第6天修复冻结，第7天演练。日期变化不允许倒填提交时间。

## 每次提交至少留四类证据

实际diff、测试结果、关联Issue/PR、对应演示或说明。每人目标是3次以上实质提交，次数只是最低计划；最终以老师实际要求和GitHub可验证记录为准。
